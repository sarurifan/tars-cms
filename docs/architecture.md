# tars-cms 架构文档

> 本文件解释 tars-cms 为什么这样设计、每个模块解决什么问题，以及新手如何从这套代码里学会 TARS。

---

## 1. 设计目标

**一句话：让新手通过一个"真实可运行的内容管理系统"，完整走一遍 TARS 企业级微服务的开发与运维链路。**

三个原则：

1. **真实** —— 不是 Hello World，每个服务都能独立部署、独立压测、独立扩容。
2. **分层清晰** —— 前端 / 网关 / 业务服务各自独立，边界明确，可单独学习。
3. **可逆可沉淀** —— 每个部署操作都是一个独立脚本，附带回滚，改坏了能退回去。

## 4. 关键技术点

### 4.1 为什么要用多种语言写不同服务

TARS 最强大的特性之一是 **多语言互调**：同一个接口定义（TARS IDL），C++/Java/Go/Node.js/PHP 各自生成代码，服务之间通过 TARS 协议透明通信。

本项目刻意混合使用：
- **auth（Go / tars_go）** —— Go 生态成熟，OIDC/JWT 库完善，适合做身份认证
- **cms（Java / tars_java）** —— Spring Boot 生态丰富，ORM 成熟，适合做业务 CRUD
- **Benchmark（C++ / tars_cpp）** —— 极致性能，官方压测工具基于 C++
- **gateway（Node.js）** —— 面向浏览器聚合，JS 生态做 BFF 最顺手

新手可以横向对比：**同一个 TARS 服务，用三种语言写，核心框架行为完全一致**。

### 4.2 网关为什么分两层

- **TarsGateway**：官方通用网关，负责 HTTP ⇄ TARS 协议转换、路由、限流、灰度。它不认识业务。
- **BFF（Backend For Frontend）**：自己的 Node.js 聚合层，面向浏览器组织数据、拼装响应。

两层各司其职：协议转换交给官方，业务编排留给自己。

### 4.3 认证为什么单独成服务

现代应用无论大小，认证都应该独立：
- 多个业务服务（cms、gateway、未来扩展）共享同一个登录态
- 认证变更（改算法、换密钥、加 MFA）不影响业务服务
- 新手能看清「登录一次，处处可用」的 SSO 原理

本项目 auth 基于 **gosso**（Go 实现的 OIDC/OAuth2 身份服务）改造，并按 TARS 要求做成真正的 **tars_go 服务**（单进程双端口：一个 TARS servant 端口供平台探测/心跳，一个 HTTP 端口供业务调用）。

### 4.4 部署为什么要「一个操作一个脚本」

TARS 的部署链路：打包 → 上传 → 配置模板 → 发布 → 验证。任一步出错，新手很难定位。

本项目的 `deploy/` 把每一步拆成独立、可逆、带回滚的脚本，同时沉淀了踩坑记录（见 `docs/pitfalls.md`）。

## 6. 学习路径（建议顺序）

1. **先看架构**（本文件 + README），理解分层
2. **部署 TARS 框架**（`deploy/` 第一步），打开管理平台看看界面
3. **部署 auth 服务**，理解「服务如何注册、心跳、被平台托管」
4. **部署 cms 服务**，对比 Java 与 Go 的差异
5. **配置网关**，看 HTTP 请求如何变成 TARS RPC
6. **跑 Benchmark**，亲手测量 QPS 和延迟
7. **改代码 → 重新发布 → 压测对比**，完成一次完整迭代
